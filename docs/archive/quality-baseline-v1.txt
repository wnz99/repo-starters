# Repository quality baseline v1

Use the working [public starter files](https://github.com/wnz99/repo-starters) with the short [adaptation prompt](python-typescript-bootstrap.md) for ordinary setup. This specification preserves the detailed v1 policy, acquisition sources and acceptance checklist. It also supports an explicitly chosen from-scratch setup; in that mode supply this full specification and its helper assets. When copying a starter, its recorded revision, manifests, native commands and documented runtime adaptations own the concrete files; do not reconstruct or overwrite them mechanically from these configuration examples.

## Determinism and inputs

Use baseline ID `wnz-repo-v1`. Copy the applicable configuration blocks, replacing only explicitly named parameters. Missing information is a pending input, not permission to invent another preset. Existing repositories get a documented mapping to their current owners; conflicting existing requirements need an explicit decision before migration.

Resolve these inputs before creating dependent configuration:

| Input | Resolution rule |
| --- | --- |
| Profile | `python-single`, `typescript-single`, or `monorepo`; supplied by the user. |
| Component inventory | Explicit unique name, relative path, language, artifact kind (`library` or `application`), and real entry points. Single repositories use path `.`; new monorepos use `apps/<name>` or the language-specific `packages/` paths from the prompt. |
| Python | Exact patch version supplied for the project, at least 3.12; derive minor-version configuration from it. Do not silently upgrade an existing supported version. |
| TypeScript target | `bun`, `node`, or `browser` per component. Bun baseline is 1.3.13. TypeScript tooling and all Nx monorepos also require Node: default 24.19.0, with `@types/node` 24.19.2 for TypeScript. A required existing Node override must supply a compatible exact runtime/type pin; do not confuse the application target with the CLI runtime. |
| CI | Existing provider, or explicit choice for a new repository. Hosted runners unless self-hosted is selected. Required operating systems are explicit inputs; do not infer Linux verification from macOS. |
| Features | Per-component `none`, `pending`, or `resolved` state for validation, Python LLM work, and MCP work; MCP client protocol and transport requirements; actual Python provider extras. |
| Optional integrations | Each has `pending`, `include`, or `exclude` plus the requested details. Pending choices never change local or remote settings. |
| Skills | Trusted source, immutable commit or installed-content digest, source subdirectory, license, destination, and selected client discovery mechanism for each required skill. No mutable `main` source or unverified download counts as a pinned installation. |

Write the resolved inputs and `baseline: "wnz-repo-v1"` to root `.bootstrap.json`. Its component list is the inventory used to generate workspace membership, native commands, Nx projects, and verification. It must contain no credentials. Record option answers there, including the target client and `repository` or `user` scope for Serena and semantic MCP configuration. Represent client config locations with repository-relative or portable home-relative paths, not another workstation's absolute username/path. A user-scope change still needs authorization. Missing executable, authentication, source, or registration permission makes an included feature incomplete; never switch it to excluded silently.

Use these exact top-level keys: `baseline`, `profile`, `purpose`, `license`, `documentationLanguage`, `runtimes`, `components`, `ci`, `options`, and `skills`. License is the supplied SPDX identifier or `pending`; never inherit this prompt's CC0 license. Create the project's LICENSE file only after its choice resolves. Documentation language is explicit; ask when unknown. `runtimes` has `python`, `uv`, `bun`, `node`, and `nodeTypes`, each an exact version string or null when unused. uv is also needed for isolated ShellCheck tooling in TypeScript-only repositories that contain shell hooks.

Each component has `name`, `path`, `language`, `target` (`bun`, `node`, `browser`, or null for Python), `artifact`, `importPackage` (Python only; otherwise null), `testDependencies`, `validation`, `entrypoints`, `runtimeDependencies` (names of components reached through runtime contracts), `llm`, and `mcp`. TypeScript `testDependencies` is an explicit map of actual test-harness packages to their declared versions, also present in the component's devDependencies; it excludes root quality tooling. It defaults to `{}` for Bun's built-in runner. Python uses its manifest's `test` dependency group and records null here. Feature objects always have `state: "none" | "pending" | "resolved"` and the user's `answer` (text or null). `llm` additionally has `providers` (objects with `name` and provider `extras`); `mcp` additionally has `protocol`, `transport`, and `clients`, nullable while pending. `validation` records whether an external-data boundary requires Pydantic. None means explicitly absent; pending is never serialized as none, an empty provider list, or null. A resolved LLM/MCP feature requires its provider/transport/client details before dependent generation. Independent quality setup can proceed with feature states pending, but complete setup cannot be claimed.

`ci` has `provider`, `operatingSystems`, and `actionRevisions`. `options` has exactly `promotion`, `merge`, `cloud`, `serena`, `semanticMcp`, and `selfHostedCi`, each an object with `state`, `answer`, and `details`. Option states are `pending`, `include`, or `exclude`; answer is the user's text or null. Details are null while unresolved. Each `skills` entry has `name`, `source`, `revision`, `subdirectory`, `license`, `digest`, and `discovery`.

Validate all resolved fields before generation: versions are exact, names and paths unique, paths relative and contained in the repository without `..`, languages/targets/artifacts are from the declared enums, and each included option has its required details. `promotion.details` contains branch/environment names and promotion rules; `merge.details` contains strategy and both cleanup booleans; `cloud.details` contains provider/accounts/projects/credential method/local-versus-CI scope; Serena/semantic details contain client, scope, version/revision, and config location; self-hosted CI details contain host, lifecycle, isolation, and access rules. Pending or excluded options have no generated configuration. An include answer with missing details stays pending. Reject unknown keys instead of silently discarding spelling errors. Sort components by path and skills by name for generated inventories; use two-space JSON indentation and a final newline.

Generate in this order: resolve inputs, render configurations/helpers, initialize language lockfiles and install pinned tools, format generated source/configuration, initialize consumer-isolation lockfiles, verify all gates, then calculate file digests and write `.bootstrap-lock.json` last. Exclude `.bootstrap.json` and `.bootstrap-lock.json` from Prettier and serialize both as two-space JSON with sorted object keys, sorted inventories, and a final newline. Do not format recorded files after hashing without recalculating their digests. Record exact direct dependency versions, tool executable versions, skill revisions/digests, and configuration SHA-256 digests. Keep records in version control when commits are authorized. Do not put transient timestamps in generated configuration. Reuse records and all language/consumer lockfiles on repeat execution. Compare current file digests before overwriting: preserve local edits and resolve differences rather than resetting them.

The lock record has exactly `baseline`, `specificationSha256`, `runtimes`, `dependencies`, `skills`, and `files`. Hash the exact supplied specification bytes as `specificationSha256`; a different specification under the same baseline ID requires an accepted revision before regeneration. `dependencies` maps manifest-relative paths to objects of direct name/version pairs. `skills` maps skill names to immutable revisions and content digests. `files` maps generated repository-relative paths to SHA-256 values, excluding the lock record itself. A skill digest is SHA-256 over sorted relative file paths and their byte digests, excluding caches. Do not include build products or local state. Lock records are refreshed only for explicitly accepted input, baseline, dependency, or generated-content changes.

Fixed configuration and direct tool pins make policy repeatable. Transitive dependency resolution on the first run can still change with registry contents; full dependency replay requires the resulting `uv.lock` and `bun.lock`. Do not claim byte-identical installs across platforms or new lockfile resolutions.

## Python policy and native wiring

Use one root `quality/pyproject.toml` for Ruff, Pylint, and pytest. Explicit CLI configuration wins over component discovery. Components must not independently redefine these tools. Approved exceptions are sparse reviewed changes to the canonical file, scoped by path where the tool supports it. Do not synthesize a generic TOML-merging script.

### `quality/basedpyright.json`

```json
{
  "pythonVersion": "{{PYTHON_MINOR}}",
  "typeCheckingMode": "strict",
  "exclude": ["**/.venv", "**/__pycache__", "**/dist", "**/build", "**/node_modules"]
}
```

Each Python component has `pyrightconfig.json`:

```json
{
  "extends": "{{ROOT_FROM_COMPONENT}}/quality/basedpyright.json",
  "include": ["src", "tests"]
}
```

`{{ROOT_FROM_COMPONENT}}` is `.` for a single repository or the computed relative path from the component to the root. Quote paths as needed in command strings. Extend this include list explicitly when maintained scripts exist; give root-owned Python tools their own configuration and target. Do not silently exclude scripts or tests to obtain a clean check.

Append the sorted unique top-level Python import package names from the inventory to Ruff's `known-first-party` list; retain `isolation_models` for the root helper. This is an input-derived name list, not a choice of policy. Do not put working-directory-dependent source globs in the shared configuration: Ruff CLI and editor discovery can interpret relative paths differently.

Root Python helpers use `pyrightconfig.tools.json` extending `./quality/basedpyright.json`, with `include: ["tools/quality/**/*.py"]` and `extraPaths: ["tools/quality"]`. Root full/static checks run `basedpyright --project pyrightconfig.tools.json`, root Ruff format/lint over `tools/quality`, and `pylint --rcfile quality/pyproject.toml tools/quality`. Root helper dependency checking is `deptry tools/quality --config pyproject.toml --known-first-party isolation_models --ignore DEP002,DEP004 --no-ansi`: helpers intentionally import root dev dependencies and do not consume every application runtime dependency. These two ignores apply only to the tooling scan; component `src` scans keep every default dependency rule.

### Component `pyproject.toml` tool blocks

Merge these blocks into the component's real PEP 621 manifest. Declare the actual distribution/import name, `requires-python`, runtime dependencies, and Hatch wheel package path. Do not infer an import path by blindly replacing hyphens; store it in the component inventory. In a workspace the root has `[tool.uv] package = false`, explicit member paths, and the root tool development group. Workspace dependency sources are explicit per internal dependency.

```toml
[tool.poe]
executor = { type = "simple" }

[tool.poe.tasks]
format = "ruff format --config {{ROOT_FROM_COMPONENT}}/quality/pyproject.toml src tests"
format-check = "ruff format --check --config {{ROOT_FROM_COMPONENT}}/quality/pyproject.toml src tests"
lint = "ruff check --no-fix --config {{ROOT_FROM_COMPONENT}}/quality/pyproject.toml src tests"
fix = "ruff check --fix --config {{ROOT_FROM_COMPONENT}}/quality/pyproject.toml src tests"
type-check = "basedpyright --project pyrightconfig.json"
```

## Required acceptance evidence

Execute these checks in disposable copies after the final changes. For Python mutation probes, disable bytecode writes and remove the disposable fixture's existing bytecode caches after mutation/restoration; same-size edits within a filesystem timestamp interval can otherwise reuse stale bytecode. Do not delete caches in the user's checkout. Record command, expected outcome, actual exit status, and relevant diagnostic in a verification section of `docs/development.md`. An acceptance result is `pass`, `fail`, or `not-run` with a reason. A failed or unrun required gate prevents a complete-bootstrap claim.

| Contract | Required probe |
| --- | --- |
| Full tool wiring | Frozen installs followed by every applicable root/component check, tests, and real builds. Record exact tool versions; fail on missing tools or no tests collected. |
| Python root policy | In every component, add a temporary local Ruff block selecting only `F`, and a source `print` call. Native lint must still fail with root `T201`. Add local weakening Pylint/pytest configuration and demonstrate the explicit root files still govern their checks. |
| Read-only lint | Enable `fix=true` in a disposable inherited Ruff config, add an unused import, and invoke the native lint task. Require nonzero/F401 and byte-identical source; restore and rerun the passing check. |
| Type coverage | Inventory maintained source/tests/scripts and compare with resolved Ruff/BasedPyright/tsc/ESLint coverage. Put a deliberate type error and lint violation in a representative file of each category and require the relevant native command to fail. |
| Real tests | Introduce a wrong expected result in an actual behavior test, require failure, restore, and require success. Test-runner or collection failure is not proof of assertion detection. |
| Python isolation | Build the component and its declared internal dependency closure as wheels. Export locked external requirements with `uv export --frozen --package <name> --no-dev --no-emit-workspace`; install them plus the built wheels in a fresh environment outside the workspace. Install the component's declared test dependencies there and run copied tests, with no sibling source paths/PYTHONPATH or root tooling site-packages. No editable install. |
| TypeScript isolation | Pack the component and its declared internal dependency closure. Install the packed artifacts and only declared test dependencies outside the workspace using the same registry/lock resolution policy. Run consumer import/startup and tests without root node_modules. Browser artifacts additionally require a browser runtime smoke test. |
| Local-state hygiene | A dummy ignored root `.agent-local.json` is allowed. Force-tracking it makes the hygiene gate fail. Also force-track a dummy ignored `.env` and require failure without reading its content. Verify Git index/ignore state without reading credentials. A selected secret-free project MCP registration is allowed and is not this local-only fixture. Restore the fixture index. |
| Nx selection | Mutate component source, each ecosystem lockfile, root language policy, a shared bootstrap/Nx file, and rename/delete a source. Check the selected project set against the known dependency graph. Invalid/missing base and failed discovery must fail or take the documented no-base full-check path. |
| Nx cache | Warm a static target, confirm its second run hits cache, then mutate its shared policy and declared dependency input separately; both must miss cache and reevaluate. Tests and integrations must execute on both runs. |
| Optional states | Included integrations perform their smoke checks. Excluded ones create no settings. Pending ones stay pending without settings; unavailable included ones report incomplete. Verify the selected client/scope rather than guessing a config path. |
| Repeat execution | Reapply with identical baseline, inputs, lockfiles, and skill revisions. No configuration changes, duplicate registrations/hooks/skills, unrelated file changes, or branch switches. Detect and preserve a deliberately edited generated file rather than overwrite it. |
| OKF | Parse all concept metadata with a YAML parser, require non-empty string type/title/description, validate navigation entries and local links, and keep `index.md` free of frontmatter. |

Exceptions are entries in `docs/development.md` with path/tool/rule, concrete reason, user decision when the contract changes, removal condition for temporary holds, and verification impact. Do not introduce a second exclusion source or silently enlarge ignores to pass the probes.
